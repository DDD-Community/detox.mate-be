## 1. 이번 작업 범위

이번 작업의 단위는 친구 관계 관리 기능이다. 초대·공유, 검색, 요청 생성, 받은 요청 조회, 수락·거절, 친구 목록, 친구 끊기를 구현·검증한다. 이미 구현된 경로는 재작성하지 않고 v3 정책에 맞는지 검증하며, 필요한 변경만 적용한다. 아래 6가지 변경은 전체 스코프가 아니라 현재 구현과 v3의 차이다. 정책의 사용자 동작과 API·필드 설계안은 구분한다.

### 포함하는 API

| API | 친구 기능에서의 역할 |
| --- | --- |
| `GET /friends/invite` | 본인의 고정 초대 코드·공유용 이메일 |
| `GET /friends/invite/{code}` | 초대 대상과 관계 상태·공개 요약 정보 확인 |
| `GET /friends/search?email=…` | 정확한 이메일 검색·관계 상태·공통 친구 확인 |
| `POST /friends/requests` | 상대에게 친구 요청 생성 |
| `GET /friends/requests/received` | 받은 요청 목록 |
| `GET /friends/requests/sent` | 기존 보낸 요청 API 유지. MVP 화면에서는 사용하지 않음 |
| `POST /friends/requests/{requestId}/accept` | 수신자의 명시적 수락 |
| `DELETE /friends/requests/{requestId}` | 수신자의 거절 |
| `GET /friends` | 내 친구 목록 |
| `DELETE /friends/{friendshipId}` | 양방향 친구 관계 해제 |

### 현재 구현에서 변경할 부분

| 변경 | 정책 근거 | 현재 코드 | 구현 계획 |
| --- | --- | --- | --- |
| 보낸 요청 목록 API 유지 | 2026-10-01 사용자 추가 지시 | `GET /friends/requests/sent` 제공 | API·조회 로직·문서·테스트 유지. MVP 화면 제외와 API 제거를 구분 |
| 발신자 취소 제외 | 3절, MVP 제외 사항 | `DELETE /friends/requests/{requestId}`가 발신자·수신자 모두 허용 | 경로는 유지하고 수신자의 거절만 허용 |
| 목록의 이메일 표시 | 3·8절 | 친구 목록·받은 요청에 이메일 없음 | `GET /friends`, `GET /friends/requests/received` 응답에 이메일 추가 |
| 수락 전 요약 통계 공개 | 3·4·8절 및 사용자 결정 | `GET /friends/invite/{code}`에 통계 없음 | 가입 당일 1일 기준 경과일·전체 성공 기록 수 추가 |
| 공통 친구 표시 | 2절 | `GET /friends/search?email=…`에 공통 친구 정보 없음 | 공통 친구 수·대표 이름 추가 |
| 공유 메시지에 내 이메일 포함 | 2절 | `GET /friends/invite`는 코드만 반환하며 `GET /users/me`에도 이메일 없음 | 내 초대 조회에 내 이메일 추가하는 방식을 제안 |

현재 구현 근거:

- [FriendController](../src/main/java/com/detoxmate/friend/controller/FriendController.java): 엔드포인트
- [FriendService](../src/main/java/com/detoxmate/friend/service/FriendService.java): 요청 상태·행위자 검사
- [FriendRepository](../src/main/java/com/detoxmate/friend/repository/FriendRepository.java): 조건부 수락·삭제
- [FriendUserResponse](../src/main/java/com/detoxmate/friend/dto/FriendUserResponse.java), [FriendInviteResponse](../src/main/java/com/detoxmate/friend/dto/FriendInviteResponse.java): 현재 응답

### 이번 변경에 포함하지 않는 것

- 친구 상세의 활동·통계·과거 피드 조회 API 신설, 피드·댓글·반응 권한 개편, 내 댓글 삭제 API 신설. 친구 관계 관리와 별도 기능이므로 이번 작업에 포함하지 않는다.
- 이름 검색 API, 친구 수·받은 요청 수 API: MVP에서는 기존 전체 목록을 프론트에서 필터링하고 길이로 표시한다.
- 친구 삭제 확인창, 받은 요청 X의 즉시 처리, 검색 중 받은 요청 숨김: 프론트 동작이다.
- 알림 정책, 링크 재발급·만료·다중 발급, 코드 수동 입력, 테이블 이름 변경.

초대 화면의 공개 요약 통계와 검색 화면의 공통 친구 정보는 친구 기능의 응답 데이터로 포함한다. 피드·상세 통계 API는 신설하지 않는다. 완료 판정은 위 10개 API를 기준으로 한다.

## 2. 유지할 동작과 데이터

- 요청 생성·수락·친구 해제 경로와 기존 상태 `NONE / SELF / PENDING_SENT / PENDING_RECEIVED / FRIEND`를 유지한다.
- 보낸 요청 API와 `PENDING_SENT`를 유지한다. 링크·이메일 재조회 시 ‘요청됨’을 표시한다. 발신자 취소는 제공하지 않는다.
- 동일 쌍의 중복·역방향 요청을 차단하고, 역방향 요청을 자동 수락하지 않는다.
- `friends`의 `from_user_id / to_user_id` 방향과 `friend_invites`의 기존 고정 코드를 유지한다.
- 이번 변경에는 새 테이블이나 마이그레이션을 기본 요구사항으로 두지 않는다. 이메일·관계 데이터는 기존 데이터를 사용한다.

## 3. 응답 설계안과 미정 사항

아래 필드명은 구현 제안이며 제품 정책의 확정 문구가 아니다.

| 응답 | 추가 필드 제안 | 범위 |
| --- | --- | --- |
| 내 친구·받은 요청 항목 | `user.email` | 해당 목록에 필요한 이메일만 제공 |
| 내 초대 | `email` | 로그인한 본인의 저장된 이메일. 기존 `code` 유지 |
| 초대 대상 조회 | `daysSinceStart`, `targetSuccessCount` | 공개가 허용된 요약 통계만 제공 |
| 이메일 검색 | `mutualFriendCount`, `mutualFriendPreviewName` | 공통 친구 전체 목록이나 이메일은 제공하지 않음 |

- 공용 `FriendUserResponse`를 일괄 확장해서 초대 대상 조회 등 다른 화면에 이메일·통계를 함께 노출하지 않는다. 필요한 응답 DTO를 분리하는 방향을 권한다.
- 공통 친구 수는 수락된 친구 관계의 교집합을 중복 없이 센다. 0명이면 대표 이름은 `null`, 화면 문구는 숨김. 1명이면 이름만, 2명 이상이면 ‘이름 외 (전체 수 - 1)명’으로 표시하는 안이다.
- 공통 친구 대표 이름은 가장 작은 사용자 ID로 고른다. 대기 요청과 탈퇴 계정은 공통 친구 집계에서 제외한다. 현재 친구 목록의 탈퇴 계정 이름·사진 가림 처리는 유지한다.
- 이메일이 없는 기존 계정은 저장된 값 그대로 `email: null`을 반환한다. 임의 이메일을 만들지 않는다. 프론트는 이메일 문구를 생략하고 초대 링크를 사용할 수 있다. OAuth 변경은 제외한다.

### 확정된 통계 기준 (2026-10-01 사용자 결정)

1. 시작 기준: 가입일. Asia/Seoul 달력 날짜의 차이 + 1 (가입 당일 1일).
2. 성공 기준: 사용자에게 속한 모든 그룹·기간의 성공한 챌린지 기록 수. 같은 날짜 여러 성공 기록도 각각 센다. 현재 탈퇴한 그룹의 과거 성공도 포함한다.
3. 활동이 없으면 가입일 기준 경과일과 성공 0회를 반환한다.

그룹별 성공 날짜 통계와 구분한다. 위 정의에 맞는 사용자 전체 집계 쿼리와 날짜 경계 테스트를 사용한다.

초대 URL 형식과 ‘친구 코드’ 명칭은 정책의 미정 사항으로 남겨 둔다. 서버의 기존 코드 발급 방식은 유지하고 공유 URL·문구는 별도로 확정한다.

## 4. 실행 순서와 완료 조건

### A0. 기존 친구 관계 관리 동작 확인

- 확인 위치: `FriendController`, `FriendService`, `FriendRepository`와 기존 테스트. 이미 구현된 요청 생성·수락·해제를 재작성하는 작업은 아니다.
- 완료 조건: 링크 조회·이메일 검색만으로 요청이나 친구 관계가 생기지 않는다. 본인 요청·동일 쌍 중복·역방향 요청은 차단되고, 받은 사람의 명시적 수락으로만 양방향 친구가 된다.
- 검증: `NONE → PENDING_SENT/PENDING_RECEIVED → FRIEND → NONE` 흐름, 본인·제삼자·발신자의 수락 차단, 수락 전 친구 목록 미노출, 수락 후 양쪽 목록 표시, 어느 한쪽의 친구 끊기 후 양쪽 목록 제거 및 재요청을 확인한다.
- 의존성: 없음. 발견한 문제는 해당 친구 관계 관리 경로 안에서 수정한다.

### A1. 발신자 요청 취소 차단

- 변경 위치: `FriendService`, `FriendRepository`, 해당 서비스·저장소 테스트.
- 서비스 검사와 조건부 DELETE 모두 `PENDING` 및 `to_user_id = 현재 사용자`를 요구한다.
- 완료 조건: 수신자 거절은 `204`, 발신자·제삼자는 `403`이고 관계 행이 유지된다. 수락된 관계는 요청 삭제로 지울 수 없다.
- 검증: 거절, 발신자 차단, 제삼자 차단, 상태 변경 및 이전 요청 ID로 새 요청을 삭제하지 못하는 사례. 기존 발신자 취소 성공 테스트는 차단 테스트로 변경한다.
- 의존성: A0에서 현재 상태 전이·권한 계약 확인.

### A2. 보낸 요청 목록 API 유지

- 유지 위치: `FriendController`, `FriendService`, `FriendRepository`, 컨트롤러 테스트와 OpenAPI.
- 보낸 요청 API는 기존 응답 형태로 유지한다. MVP 화면 제외 정책을 API 삭제로 해석하지 않는다.
- 완료 조건: 인증한 발신자는 자신의 대기 요청 목록을 조회할 수 있다. 조회 가능 여부와 취소 권한은 별개다.
- 검증: 목록·문서 유지, 수락/거절 후 대기 목록 제거, 재조회 관계 상태 유지.
- 의존성: A1 이후 하나의 변경 묶음으로 검증.

### A3. 친구·받은 요청 목록 이메일

- 변경 위치: 응답 DTO, `FriendResponseMapper`, 컨트롤러 테스트.
- 완료 조건: 각 목록 항목에서 해당 상대의 저장된 이메일을 반환하며 요청 ID·친구 관계 ID·기존 관계 상태를 유지한다.
- 검증: 목록 이메일, 빈 목록, 탈퇴 계정 처리와 초대 대상 조회에서 불필요한 이메일이 노출되지 않는지 확인한다.
- 의존성: 응답 필드 계약 정리. 이메일 없는 계정은 nullable로 처리.

### A4. 공유용 내 이메일

- 변경 위치: `FriendInviteResponse`, `FriendService`, 해당 테스트.
- 완료 조건: 기존 고정 코드와 본인 이메일을 반환한다. 반복 조회에도 코드가 바뀌지 않고 다른 사용자 이메일을 반환하지 않는다.
- 검증: 신규 코드 생성·기존 코드 재사용·본인 이메일 확인.
- 의존성: A3의 이메일 없는 계정 처리 기준과 일치.

### A5. 이메일 검색의 공통 친구

- 변경 위치: 검색 응답 DTO, 서비스, 친구 조회 쿼리, 해당 테스트.
- 완료 조건: 정확 일치 검색·관계 상태를 유지하며 공통 친구 수·대표 이름을 반환한다. 0명·1명·여러 명을 구분한다.
- 검증: 양방향 저장 관계의 교집합, 중복 제외, pending 제외, 비활성 계정 제외, 이미 친구·자기 자신·검색 실패의 기존 동작. 친구별 개별 조회 반복 대신 한 번의 집계 또는 배치 조회를 사용한다.
- 의존성: 응답 필드 계약 정리. 새 공통 친구 테이블은 만들지 않는다.

### A6. 초대 대상 요약 통계

- 변경 위치: 초대 응답 DTO, 서비스, 기존 활동 데이터 집계 쿼리, 해당 테스트.
- 완료 조건: 확정된 정의로 두 통계만 반환한다. 친구 수락이나 해제에 따라 활동 집계 값이 임의로 바뀌지 않는다.
- 검증: 고정 Clock으로 날짜 경계·활동 없음·성공/실패 기록·중복 집계·타 사용자 기록 제외를 확인하고 비친구 상태에서도 허용된 요약만 반환한다.
- 의존성: 3절의 통계 기준 확정. 확정 전에는 숫자를 임의 구현하지 않는다.

### 최종 확인

1. 생성된 OpenAPI에 보낸 요청 목록이 유지되고, 요청 DELETE가 수신자 거절로 설명되어 있다.
2. 이메일·공통 친구·초대 요약 통계의 필드와 nullable 조건이 문서 및 실제 응답과 일치한다.
3. 두 사용자 A/B와 공통 친구 C로 ‘초대 조회·공유 데이터 확인 → 검색 → 요청 → 받은 요청 조회 → 재조회 → 발신자 거절 시도 차단 → 수신자 거절 → 재요청 → 수락 → 양쪽 친구 목록 확인 → 친구 해제 → 양쪽 목록 제거’를 확인한다.
4. 고정 초대 코드, 중복·역방향 요청 차단, 과거 요청 ID의 오용 방지가 회귀하지 않는다.
5. FE의 현재 호출 경로를 확인하고 응답 추가 및 발신자 취소 차단을 PR에 문서화한다. 이번 작업에서 API 경로는 제거하지 않는다.

검증 결과는 실행한 명령·환경·성공/실패·미확인 항목을 기록한다. H2 테스트만으로 MySQL의 함수 인덱스·동시성까지 검증했다고 주장하지 않는다. 쿼리나 잠금 변경으로 관련 우려가 생기면 격리된 MySQL에서 해당 사례만 추가 확인한다. 실제 사용자 데이터를 검증용으로 수정하지 않는다.
