# 친구 v2 DB 설계 — MVP

결정: `from_user_id`, `to_user_id`로 요청 방향을 저장한다. 요청과 친구 관계는 `friends` 한 테이블에서 관리한다. `low/high` 컬럼이나 별도 친구 요청 테이블은 만들지 않는다.

DDL: [2026-09-14-friends-v2.sql](2026-09-14-friends-v2.sql)

MySQL 8.4 기준 설계 초안이다. 자동 마이그레이션이나 기존 데이터 이관 스크립트가 아니다. 사용자 데이터 재설계는 제외하며, 실행 전제인 사용자 키는 저장소의 `users.user_id` / BIGINT에 맞췄다.

## 테이블

### friend_invites — 사용자별 고정 초대 링크

| 컬럼 | 의미 |
| --- | --- |
| id | 초대 식별자 |
| user_id | 초대 소유자 |
| code | URL에 넣는 초대 코드 |
| created_at | 발급 시각 |

- 서버에서 안전한 난수 32바이트를 생성해 64자리 소문자 hex로 인코딩한다. 이메일·사용자 ID로 코드를 만들지 않는다.
- `code`는 전체에서 유일하다. 유효한 코드로 초대 소유자의 이름·사진을 확인한 뒤 친구 요청을 보낸다.
- MVP에서는 `user_id`도 UNIQUE: 사용자당 하나이며 여러 사람이 재사용할 수 있다. 자동 만료·재발급·수동 코드 입력은 없다.
- 향후 여러 초대가 필요하면 사용자 고유 제약을 제거해 1:N으로 확장한다. 미래 기능의 컬럼은 미리 만들지 않는다.
- 링크 공유 메시지에는 이메일을 함께 표시한다. 코드가 노출되어도 친구의 기록을 바로 읽을 수는 없고, 수락이 필요하다.

### friends — 대기 요청 또는 수락된 관계

| 컬럼 | 의미 |
| --- | --- |
| id | 이번 요청·관계의 식별자 |
| from_user_id | 요청을 보낸 사람 |
| to_user_id | 요청을 받은 사람 |
| status | `PENDING` 또는 `ACCEPTED` |
| created_at | 요청 생성 시각 |
| updated_at | 마지막 변경 시각 |
| accepted_at | 수락 시각. 대기 중에는 NULL |

- 한 행이 두 사람 사이의 관계 하나다. 수락해도 `from/to`는 바꾸지 않고, 반대 방향의 행을 추가하지 않는다.
- 애플리케이션 상태값은 `PENDING`, `ACCEPTED`로 저장한다. `ACCEPTED`면 양방향 친구이며 과거 피드·통계·히스토리까지 공개한다. `PENDING`은 친구가 아니다.
- `(from,to)` UNIQUE만으로는 `(A,B)`와 `(B,A)`를 막지 못한다. `LEAST/GREATEST` 함수식 고유 인덱스로 순서와 무관하게 한 쌍만 허용한다. 이는 저장 컬럼을 low/high로 바꾸는 것이 아니다.
- 본인 요청, 허용되지 않은 상태, 상태와 수락 시각의 불일치는 CHECK 제약으로 막는다.
- 거절·취소·친구 끊기는 행 삭제. 재요청은 새 id로 생성한다. 거절·취소·끊기 이력은 저장하지 않는다.

## 동작 규칙

| 행동 | 권한·현재 상태 | 처리 |
| --- | --- | --- |
| 요청 | 본인이 from. 본인·탈퇴 사용자 대상 금지 | pending 생성. 이미 어느 방향의 행이 있으면 새 요청 불가 |
| 수락 | 본인이 to이고 pending | accepted로 변경하며 accepted_at 기록 |
| 거절 | 본인이 to이고 pending | 삭제 |
| 취소 | 본인이 from이고 pending | 삭제 |
| 친구 끊기 | 본인이 둘 중 한 명이고 accepted | 삭제 |

로그인 사용자 ID는 서버에서 얻는다. 클라이언트가 전달한 요청자 ID를 신뢰하지 않는다. 요청 생성 전 조회는 안내용이며, 동시에 들어오는 중복 요청은 고유 제약 위반도 처리해야 한다. 반대 방향 요청을 자동 수락하거나 덮어쓰지 않는다.

변경·삭제는 **id + 현재 상태 + 행위자**를 한 SQL의 조건에 넣고 영향받은 행 수를 확인한다. 예전 요청의 취소가 새로운 재요청을 삭제하지 않도록 id를 사용한다.

```sql
-- :me, :id는 서버의 바인딩 파라미터 표기다.
UPDATE friends
SET status = 'ACCEPTED', accepted_at = CURRENT_TIMESTAMP(6)
WHERE id = :id AND to_user_id = :me AND status = 'PENDING';

DELETE FROM friends
WHERE id = :id AND from_user_id = :me AND status = 'PENDING';
```

## 조회와 인덱스

- 보낸 요청: `from_user_id = :me AND status = 'PENDING'`.
- 받은 요청: `to_user_id = :me AND status = 'PENDING'`.
- 친구 목록: `status = 'ACCEPTED' AND (from_user_id = :me OR to_user_id = :me)`.
- 상대 ID는 from이 나이면 to, 아니면 from이다.
- 양쪽 `(사용자 ID, status)` 인덱스를 둔다. 정렬용 대형 인덱스나 조회용 복제 테이블은 이번 DDL에서 제외한다. 목록은 페이지 단위로 제공하고, 정렬 정책에 맞춘 튜닝은 실제 조회를 측정한 뒤 결정한다.
- 기존 PostgreSQL 벤치마크의 시간과 실행 계획은 MySQL에 그대로 적용할 수 없다.

프로필·피드 접근은 현재 accepted 관계로 판단한다. 초대 확인·이메일 검색에서는 이름·사진만 보여준다. 친구의 피드에서 비친구의 댓글·반응은 볼 수 있지만 그 사람의 상세 프로필에는 들어갈 수 없다.

댓글·이모지 반응은 친구 행에 종속시키지 않고 게시물과 작성자를 참조한다. 친구 행 삭제가 댓글·반응을 삭제하지 않아야 한다. 본인 댓글 삭제는 제공하며, 별도 활동 관리 화면과 목표 미달 알림의 상세 설계는 범위 밖이다.

## 이메일과 사용자 테이블의 경계

이메일 정확 일치 검색 → 상대 확인 → 친구 요청 흐름은 유지한다. 검색용 이메일은 `users.email`에 저장하고, 대소문자와 앞뒤 공백을 정규화한 뒤 유일하게 관리한다. 카카오 계정 응답과 Apple identity token에서 서버가 검증한 이메일만 저장하며, 검색 결과에는 이메일을 다시 노출하지 않는다.

기존 사용자는 `users.email`이 NULL일 수 있다. 이번 기능의 수동 마이그레이션은 이메일 컬럼과 유일 인덱스를 nullable로 추가하고, 사용자가 다음에 검증된 소셜 로그인을 할 때 비어 있는 이메일을 보완한다. 탈퇴한 사용자는 검색 대상에서 제외하고 이메일을 비운다.

서로 다른 소셜 계정이 같은 이메일을 제출해도 자동 계정 병합은 하지 않는다. 이미 다른 사용자에게 등록된 이메일이면 로그인 요청을 `409 Conflict`로 거절한다.

## 검증

별도 MySQL 8.4.8 테스트 DB에서 DDL 생성과 아래 동작을 확인했다. 실제 앱 DB에는 적용하지 않았다.

- PASS: 사용자별 초대 하나, 초대 코드 중복 금지, 존재하지 않는 사용자 참조 차단.
- PASS: 동일·역방향 관계 중복 금지, 본인 요청 금지, 상태·수락 시각 제약.
- PASS: 수신자만 수락, 수락된 행에 대한 요청 취소 무효, 친구 끊기 후 새 요청 생성, 이전 id로 새 요청 삭제 불가.
- PASS: 독립 문서·DDL 검토.
- NOT RUN: 실제 애플리케이션 연동, 동시 요청 부하, 이메일 검색 구현.
